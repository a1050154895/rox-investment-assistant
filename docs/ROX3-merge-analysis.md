# ROX3.0-Quant（前身）与现工作台综合分析

> 前身仓库：https://github.com/a1050154895/ROX3.0-Quant.git
> 分析日期：2026-08-22 ｜ 用于升级过程中持续辩证，结论按"能结合 / 不能结合"给出理由。

---

## 一、两个项目是什么关系

| | ROX3.0-Quant（前身） | 现工作台（ROX 投资助手） |
|---|---|---|
| 定位 | 大而全的量化平台（行情+策略+回测+AI+知识库+桌面端+会员） | 证据优先的个人投研工作台（研究卡→证据→决策→复盘闭环） |
| 规模 | app/ 232 个 py 约 6.75 万行 + 127M 数据文件 | 约 40 个 py + 轻量 SPA |
| 架构 | FastAPI + Jinja2 多页（16 个模板，含 /classic /pro 双壳） | FastAPI + vanilla JS 单页 |
| 数据观 | **mock 数据混入真实链路**（失败时返回随机数不标注） | 数据可信原则（不可用就显示不可用，快照不冒充实时） |
| 测试 | tests/ 172 用例 + 根目录 40 个临时脚本 | 123 用例，全绿，CI 完整 |
| 状态 | 单 squash 提交，v3.4 后停滞；自检报告承认 Level2=随机数、无实盘 | 活跃开发中（v4.14.0，Render 线上） |

前身不是垃圾堆，里面有几块**真材实料**；但它的整体方向（对标同花顺/聚宽的大平台）与现工作台的定位（证据优先、诚实降级）相悖。合并原则：**搬零件，不搬架构；搬实现，不搬理念。**

## 二、能结合的部分（按价值排序）

### 1. 回测引擎（最值得搬）★★★★★
- **是什么**：`app/rox_quant/backtest_engine.py`（561 行）——K 线重放、手续费/滑点/印花税/最低佣金、止损止盈、夏普/最大回撤/胜率/盈亏因子；配套 `portfolio_backtest.py`（组合回测）、`performance_metrics.py`。
- **为什么能结合**：现工作台有 `/api/backtest` 路由但引擎很薄；前身的费用模型和绩效指标是纯计算、无外部依赖、有测试（`test_p3_5_backtest.py` 等），与新工作台"回测结果必须可审计"的调性一致。
- **怎么结合**：把 `BacktestEngine` + 绩效指标抽成独立模块（`app/services/backtest_v2.py`），输入统一为现有 K 线契约格式；回测结果落库并与研究卡关联（"这个判断历史上胜率如何"）。输出必须带样本数、费用假设、免责说明。
- **工作量**：中（1-2 天，主要是适配数据契约 + 测试搬运）。

### 2. 通达信风格技术指标库 ★★★★☆
- **是什么**：`app/analysis/indicators.py`（404 行 30 个函数）——MA/EMA/MACD/KDJ/RSI/BOLL/WR/CCI，以及通达信特有的 **ZIG/PEAK/TROUGH（之字转向）、BARSLAST/FILTER/BACKSET/COUNT**；另有 `technical_indicators.py` 的 7 个信号模板（双均线/MACD/RSI/布林/KDJ/动量/均值回归）。
- **为什么能结合**：现工作台只有 RSI/KDJ/MACD/均线/布林五样；这些是纯函数、易测试。ZIG/PEAK/TROUGH 对"高点低点标注"（研究卡的失效条件可视化）有直接用途。
- **怎么结合**：挑选与现有 `analysis_engine.py` 风格一致的函数迁入；**每个指标必须写数值测试**（用已知序列断言输出），因为这类代码最容易出现 off-by-one 和未来函数（ZIG 本身就是事后修正型，必须标注"含未来数据，不可用于回测信号"）。
- **工作量**：小-中（半天-1 天）。

### 3. 多 Provider AI 客户端（BYOK 增强参考）★★★★☆
- **是什么**：`app/rox_quant/llm.py`（426 行）——AsyncOpenAI 多提供商封装：环境变量+JSON 扩展注册、base_url 自动补 `/v1`、主备 failover、RAG 上下文注入。
- **为什么能结合**：现工作台 v4.13.0 刚做了三档 AI 模式（off/platform/byok），但 BYOK 只支持单一 endpoint；前身的**多提供商注册 + failover** 设计正好补强 byok 层。
- **怎么结合**：只借鉴它的 provider 注册结构和 failover 逻辑，融入现有 `ai_service.py`；**不搬** `analyze_stock`（它失败时回退"本地规则假数据"冒充 AI 结论，违反数据可信原则）。
- **工作量**：小（半天）。

### 4. AKShare 限流包装器 + 东财降级 ★★★☆☆
- **是什么**：`app/utils/akshare_wrapper.py`（5QPS 限流+重试）、`ashare_fallback.py`（东财行情/K 线降级）、`datasources/ashare_lite.py`（162 行腾讯/新浪直连，统一 `get_price()`）。
- **为什么能结合**：现工作台 v4.11.0 的 DataSourceRegistry 已有健康埋点，但缺少**限流**和东财降级链。前身的 wrapper 是现成实现。
- **怎么结合**：把限流/重试并入现有 akshare 调用路径；东财作为行情降级链的一环登记进 DataSourceRegistry（`degrade_to` 已有字段）。**逐行检查剥离任何 random 分支。**
- **工作量**：小（半天）。

### 5. 宏观指标并行抓取（时效参考）★★★☆☆
- **是什么**：`app/rox_quant/macro_data.py`——中债 10Y、PMI、CPI、PPI、M2、美元人民币**并行抓取 + 3s 超时隔离**。
- **为什么能结合**：现工作台宏观指南针串行抓取偏慢（性能报告里提过）；它的并行+超时隔离模式值得吸收。它缺的指标（中债收益率、汇率）也是现工作台宏观矩阵想要的。
- **怎么结合**：借它的 `asyncio.gather + 超时` 骨架重构现有 `macro_data.py`；**必须删掉"静态默认值兜底"**——它失败时返回写死的默认数字，这在现工作台是红线（不可用就 unavailable）。
- **工作量**：小（半天）。

### 6. 策略文库（作为知识资产）★★★☆☆
- **是什么**：`app/data/documents/strategies/` 100 篇聚宽社区策略 + 27 本书籍（达利欧《债务危机》《原则》、卢麒元文集等）。
- **为什么能结合**：现工作台认知框架页有"知识库"，内容是自写的；这批语料可以作为**研究素材**（用户学习参考），对应顶层设计"策略库/知识库"。
- **怎么结合**：**不进 git**（127M + 版权风险，仅自用）。可以做一个"本地知识库目录"功能：用户自己放入书籍/策略文本，系统建索引供检索；仓库只带索引器代码（`knowledge_base.py` 的 docx/pdf 解析 + jieba 关键词匹配可精简后复用）。
- **工作量**：中（按需再做）。

### 7. ETF 轮动/小市值策略逻辑（作为策略知识，不移植代码）★★☆☆☆
- **是什么**：`jq_etf_rotation.py`（动量轮动）、`jq_small_cap.py`、书内策略（海龟/双均线/Dual Thrust）。
- **为什么能结合**：等回测引擎（第 1 项）迁移后，这些策略**思想**可以在新引擎上重写为带明确假设/失效条件的研究模板，正好挂到研究卡体系。
- **怎么结合**：只迁"策略描述+参数+逻辑说明"，代码在新引擎重写；每个策略必须先通过"它凭什么赚钱"的研究卡拷问。
- **工作量**：大（按需逐个做）。

## 三、不能结合的部分（及理由）

### 1. mock 数据链路 ❌ 绝对不能
`market_data.py:72-111` 指数/涨跌家数失败时返回**随机数且不标注**；`level2-sim` 五档全是随机；诊断分数带随机扰动。这是前身自己的检查报告都承认的问题（"Level2 五档 = 随机数模拟"）。现工作台的核心价值观就是"不伪造数据"，任何 random 分支一律剥离，无讨论空间。

### 2. 聚宽策略执行体系（jq_adapter + exec 注入）❌
用 `sys.modules['jqdata'] = mock` 注入后 `exec()` 运行聚宽代码：get_fundamentals 返回空 DataFrame、get_industry 空、策略文件是 notebook 风格。**exec 执行任意代码 + 数据适配半成品**，安全和正确性双输。策略思想可以重写（见二.7），执行体系不搬。

### 3. 通达信 DLL 桥 ❌（现阶段）
`tdx_bridge/main.cpp` 拿不到股票代码（发 "UNKNOWN"），Python 侧 `calculate_signal` 是占位假逻辑（价格尾数 .00 买 .50 卖）。Windows-only、双进程、毫秒延迟。等有真实 Windows 用户需求且信号逻辑真实后再议。

### 4. A2A 玩具生态（ai_traders 人格/AI 评论/交易模拟）❌
10 个 AI 交易员人格、情绪参数、模拟对话——与"帮助用户自己想清楚"的产品定位相悖，纯娱乐化，且模拟生态会被误读为真实能力。顶层设计已明确"不做社交炒股平台"。

### 5. OpenClaw / AllTick 集成 ❌
依赖 localhost:18789 的实验性外部框架；AllTick 是付费服务且**硬编码 token 已泄露在仓库里**（alltick_client.py:499，该 token 应视为已作废并轮换）。外部付费/实验依赖不符合现工作台"公开接口+诚实降级"的数据策略。

### 6. 会员系统/商业化代码 ❌
顶层设计明确：商业化必须放在数据授权、合规和核心留存验证**之后**。前身的 membership/OpenClaw 数据服务是最后一步开发即止的半成品，不搬。

### 7. 双数据库/多入口/巨页前端等架构遗留 ❌
SQLite 与 PostgreSQL schema 不统一、端口 8008/8081/8099 三处不一致、100KB 单页模板、`.secret_key` 真实密钥入库、根目录 40 个 debug/test 临时脚本、三套并存的策略体系。这些是反面教材：现工作台的 monorepo 纪律（123 测试全绿、flake8 干净、单一入口）要守住。

### 8. "东方智慧/寻龙诀/亢龙有悔"等概念指标 ❌
无实盘验证、无文献支撑的玄学命名规则引擎（eastern_wisdom.py 1709 行等）。现工作台的方法论（五层认知/334 纪律）已有实现且与顶层设计一致，不再叠加 unverifiable 的概念模块。

## 四、升级过程中的辩证原则（ checklist ）

从前身搬任何东西前，依次过四道门：

1. **数据可信门**：代码里有没有 random/mock/写死默认值冒充真实数据？有 → 剥离或放弃。
2. **依赖门**：是否引入外部平台/付费服务/localhost 实验？有 → 默认放弃，除非有明确授权和降级路径。
3. **证据链门**：搬进来后能否接入研究卡-决策-复盘闭环？接不上的（纯展示、纯娱乐）→ 不搬。
4. **测试门**：能否为其写出确定性数值测试？写不出（如 exec 注入、DLL 桥）→ 不搬。

## 五、建议吸收顺序

1. 回测引擎 v2（结合研究卡：判断的历史验证）
2. 通达信指标函数库（补齐 ZIG/PEAK 等，全部带数值测试）
3. BYOK 多提供商 failover
4. AKShare 限流 + 东财降级链（并入 DataSourceRegistry）
5. 宏观并行抓取重构（去静态默认值）
6. （按需）本地知识库索引器、策略知识重写
